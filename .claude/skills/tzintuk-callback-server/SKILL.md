# שרת המענה לצינתוקים — השלמה ותחזוקה בטוחה

מנגנון "הצינתוק הזול": צינתוק קלאסי (‎0.1 יח') מצלצל → הזכאי חוזר לצלצל ל-04 →
עובר דרך שלוחה **/76** (`type=api`) → Worker ב-Cloudflare עונה אישית ("יש לך
חלוקה… 1 מגיע / 2 לא / 3 לא יודע") ושומר את ההקשה ב-D1 → התוכנה מושכת ב-
`GET /answers` וממזגת ל-`yemot.fetch_survey_rows` (אותם תגי "אישר הגעה"/היסטוריה/אקסל).

## ⚠️ שערי בטיחות — לקרוא לפני כל פעולה על הקו

1. **שורש הקו = המקום הכי מסוכן.** שתי תקריות (3/9, 8/9) נבעו מכתיבות/הגדרות בשורש.
   הכלל הקבוע: שינוי בשורש **רק** עם (א) אישור/ידיעת המנהל השני (רון — הקו משותף;
   הוא מחזיק סיסמת קו מלאה), או הכרעה מפורשת של הבעלים; (ב) **התוכנה סגורה בשני
   המחשבים**; (ג) גיבוי טרי + diff + אישור מפורש לכל כתיבה; (ד) קריאה חוזרת לאימות.
2. **הכלל המערכתי:** התוכנה **לא** כותבת לשורש אוטומטית (המנגנון הישן של שלוחה 78
   נעול, `yemot.CALLBACK_ENABLED=False`). כתיבה לשורש = ידנית ומכוונת בלבד.
3. **WHITELIST = כלל זהב** (תקרית 8/9): ברירת-המחדל של הקו חייבת להישאר "קופה"
   (`incomingPolicy=OPEN`). אם מישהו מריץ סבב גבייה עם רשימה סגורה — כל הקו חסום
   לכולם ("המספר לא זמין"). ראה `yemot-campaigns-ivr`. אמת ב-`get_system_overview`
   שהקו עונה לפני/אחרי כל שינוי.

## 3 הצעדים שנותרו להשלמה (בסדר הזה בלבד)

**סדר קריטי: מונע-הלולאה לפני הניתוב** — כך אף רגע אין ניתוב בלי מונע-לולאה.

1. **שורש `ext.ini` ← מונע-לולאה.** להוסיף שורה אחת: `check_did_and_go_to_folder_one_time=yes`.
   שלב זה לבדו **לא משנה התנהגות** (אין עדיין ניתוב ל-/76) — מצב-ביניים בטוח.
2. **`Did_Go_To.ini` ← ניתוב.** להוסיף שורה: `048691834=/76` (לא למחוק את `033060315=/555`).
   מרגע זה כל מחייג ל-04 עובר קריאה אחת ל-/76 (‎~0.5 שנ', בלי מוזיקת המתנה).
3. **מתג בתוכנה ← דלוק.** הגדרות → "שרת המענה" → הדלקה (`cb_server_enabled=1`); אז
   push דוחף רשימות בכל שליחה/תזמון, ו-answers מתמזג. בדיקה חיה: חיוג ל-04 מ-0556752642.

אחרי כל צעד: בדיקת-תקינות (קריאה חוזרת + `get_system_overview` שהקו עונה).
מדריך ביצוע מלא + rollback: `references/reconnect.md`. הרצת בדיקה: `scripts/check_callback.py`.

## למה הסדר הזה בטוח (מכניקת הלולאה — מאומת 9/9)

- `check_did_and_go_to_folder` הוא **פר-שלוחה**, רק בשורש. `/2` (שאליו נופלים
  ברירת-מחדל) הוא `type=routing` בלי הדגל.
- /76 מחזיר `go_to_folder=/` → המתקשר חוזר לשורש → הדגל מפעיל שוב את Did_Go_To →
  שוב /76 → **לולאה**. `check_did_and_go_to_folder_one_time=yes` = "דילוג פעם אחת
  בשיחה" (f2 post/60) → Did_Go_To יורה רק בכניסה הראשונה. **חובה.**
- לא ניתן לעקוף ע"י החזרת יעד לא-שורשי מה-Worker: החזרת `/2` תדלג על הברכה
  (`campaign_message_to_play`) לכל מחייגי 04 ותשבור את הודעות הקמפיין של רון.

## הממצא המכריע (מנוטרל סיכון) — השורש נכתב מחדש אוטומטית, אבל בבטחה

השורש **משתנה לבד** (נצפה 09/09 12:25): מנגנון הודעות-הקמפיין מעדכן את השורה
`campaign_message_to_play=N-ACTIVE` כשקמפיין נדלק/נכבה (לא רון ידנית). **אבל** השוואה
בייט-אחר-בייט בין השורש של היום לגיבוי של 8/9 הוכיחה שזו **עריכת-שורה כירורגית** —
מחליף רק את שורת הקמפיין, שומר כל שאר המפתחות והשורות הריקות. לכן:
- מונע-הלולאה שנוסיף **ישרוד** את הכתיבות-מחדש (כמו ש-`check_did_and_go_to_folder=yes`
  שרד). שורת הניתוב יושבת בקובץ **נפרד** (`Did_Go_To.ini`) שהמנגנון לא נוגע בו.
- סיכון שארי יחיד: אם רון יערוך את הברכה דרך טופס שמרנדר מחדש את כל ה-ext.ini → עלול
  להשמיט מפתחות לא-מוכרים. הוכחה עד כה שזה לא קורה, אבל זו הסיבה לעדכן אותו / לבדוק
  תקופתית עם הבודק.

## השיטה הטכנית לכתיבה לשורש (חשוב!)

- ה-MCP `pitron-ivr` **חוסם** `write_text_file` ו-`plan_extension_changes` ל-`ext.ini`
  ("כתיבת ext.ini אינה מותרת כאן"). אל תנסה לעקוף דרכו.
- כתיבה בייט-מדויקת (השיטה הקבועה, שבה נכתבו /76 והתיקון של 3/9):
  `yemot._upload_multipart("ivr2:/ext.ini", new_bytes, convert="0")` — כותב בדיוק את
  הבייטים שלך, שומר את שורת הברכה של רון מילה-במילה.
- **תמיד: קרא טרי מיד לפני הכתיבה** (`yemot._download`) כי שורת הקמפיין עלולה
  להשתנות, הוסף רק את השורה החסרה, כתוב, **קרא חוזר ואמת diff מדויק** (רק שורה אחת
  נוספה, שום דבר לא נמחק). גיבוי טרי לפני: `dev/line_change_2026-09-10_callback_route/`.
