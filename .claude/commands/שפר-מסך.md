# שיפור UX למסך — תכנון, אישור, מימוש

מטרה: לקחת **מסך אחד** בתוכנה, להבין איך הוא נראה ומרגיש היום, להכין **תוכנית שיפור עצום** בחווית המשתמש,
להציג אותה ליהודה בשפה פשוטה עם הדמיה, **לעצור ולחכות לאישור** — ורק אז לממש, לאמת בצילום אמיתי ולשחרר.

המסך לשיפור: **$ARGUMENTS**

## שלב 0 — איזה מסך
- אם `$ARGUMENTS` ריק או עמום → **שאלה ממוקדת אחת** (AskUserQuestion) עם רשימת המסכים לבחירה:
  חלוקה ורישום (`tabs/group_update.py`) · כל המקבלים (`tabs/recipients.py`) · חיפוש מהיר (`tabs/search.py`) ·
  חלוקות קודמות (`tabs/distributions.py`) · הודעות (`tabs/messages.py`) · צינתוקים (`tabs/tzintukim.py`) ·
  מיילים (`tabs/mails.py`) · הגדרות (`tabs/settings.py`) · דיאלוג ספציפי (לציין שם). **לא לסרוק את כל הפרויקט.**
- טען סקילים: `manhal-haluka` (כללי הפרויקט), `visual-check` (מתכון צילום), `feature-impact` (מה זה שובר).

## שלב 1 — המצב הקיים (קריאה בלבד)
1. קרא **רק** את קובץ המסך (ודיאלוגים שהוא פותח). לא לגעת בלוגיקה — למפות מה ווידג'ט, מה signal, מה attribute
   ששאר הקוד/הבדיקות מסתמכים עליו (`grep` על שם ה-attribute ב-`tabs/`, `main.py`, `test_*.py`, `dev/`).
2. **צילום אמיתי** של המסך כפי שהוא היום: השתמש בסקריפט צילום קיים ב-`dev/_shot_*.py` אם יש לאותו מסך,
   אחרת כתוב אחד לפי המתכון ב-`visual-check` (DB זמני מזורע, `WA_DontShowOnScreen` + `grab()`, **לא offscreen**).
   ⚠ **אל תקרא את ה-PNG לתוך הצ'אט** (מלכודת נטפרי) — נתח אותו דרך `gemini_task.py -f <png>` ובקש ביקורת UX
   מפורטת בעברית (היררכיה, צפיפות, בהירות, מה מבלבל משתמש לא-טכני).
3. הצלב עם **שפת העיצוב הקיימת** של התוכנה (הסטנדרט: צינתוקים / הגדרות v3.01 / חלוקה-ורישום v3.03 —
   כותרת+צ'יפי-סטטוס חיים, כרטיסים לבנים ממוספרים ①②③, סרגל תחתון קבוע, עזרי `_step_card`/`_metric`
   מ-`group_update.py`). מסך שסוטה מהשפה הזו — זו כבר בעיה.

## שלב 2 — ביקורת UX (מה באמת כואב)
עבור על המסך לפי הרשימה הזו וכתוב ממצאים קונקרטיים (לא כלליים):
- **המשימה העיקרית** — מה המשתמש בא לעשות במסך הזה? כמה קליקים/גלילות זה דורש? מה מסיח?
- **היררכיה ויזואלית** — האם הדבר החשוב הכי בולט? כפתור ראשי אחד ברור? פעולות מסוכנות מרוחקות/אדומות?
- **מצבים** — ריק (אין נתונים), טעינה, שגיאה, הצלחה: האם כל מצב אומר למשתמש מה קורה ומה לעשות?
- **משוב** — אחרי פעולה, האם רואים שהיא קרתה (צ'יפ/תג/הודעה)? או שהמסך "שותק"?
- **שפה** — טקסטים בעברית פשוטה למנהל לא-מתכנת; בלי ז'רגון, בלי קיצורים, בלי מספרי-קוד.
- **RTL ופריסה** — יישור, סדר עמודות, רוחב מסך (לא רחב מהחלון), גלילה אחת ולא חלון-בתוך-חלון.
- **עקביות** — אותם כפתורים/צבעים/מיקומים כמו בשאר המסכים; אותו גופן (Segoe UI בלבד).
- **גילוי (discoverability)** — תכונות שקיימות אבל חבויות; הגדרות שצריך לחפש.
- **נגישות/קריאות** — ניגודיות, גדלי-טקסט (מכבד `ui_font_scale`), ריווח, טבלאות עמוסות.

## שלב 3 — תוכנית שיפור (הצג ועצור)
בנה תוכנית **שאפתנית אך מציאותית** — לא ליטוש אלא קפיצת-מדרגה בחוויה, בגבולות "עיצוב + זרימה", **בלי לשנות
כללים עסקיים/נתונים/סנכרון** (אם שיפור דורש שינוי כזה — ציין אותו כפריט נפרד עם אזהרה, ותן ליהודה להכריע).
הצג ליהודה **בעברית פשוטה**:
1. **מה כואב היום** — 3–7 נקודות, כל אחת במשפט ("כדי לעשות X צריך 4 קליקים ולגלול").
2. **מה יהיה אחרי** — תיאור המסך החדש בזרימה: מה למעלה, מה באמצע, מה בסרגל התחתון; מה נעלם/מתקפל/עולה.
3. **הדמיה** — קובץ HTML סטטי בשורש הפרויקט בשם `הדמיית_<מסך>.html` (כמו `הדמיית_צינתוקים.html`/`הדמיית_מיילים.html`
   שאושרו בעבר): RTL, צבעי התוכנה (primary ‎#0f9d78‎, רקע ‎#f4faf7‎, כתום ‎#f59e0b‎), נתוני-דמה. פתח אותו
   ב-Browser pane וצלם/אמת שהוא נראה כמו שתיארת. זה מה שיהודה מאשר.
4. **מה לא משתנה** — במפורש: כללים עסקיים, נתונים, סנכרון, שמות attributes/signals (הבדיקות והמסכים האחרים
   ממשיכים לעבוד).
5. **סיכונים ומחיר** — מה עלול להישבר, כמה זמן, האם צריך גרסה חדשה/צילומים חדשים/עדכון סקילים.
6. **שאלות הכרעה** — רק אם יש באמת שתי דרכים שונות מהותית; אחרת תמליץ ותגיד למה.

**עצור כאן.** סיים בשורה אחת: "לאשר ולהתחיל? (אפשר לאשר חלקית — לציין מספרי סעיפים)". **אין לכתוב קוד לפני
אישור מפורש** בצ'אט. אישור חלקי = לממש רק את מה שאושר.

## שלב 4 — מימוש (אחרי אישור בלבד)
- עבוד לפי `feature-impact`: לפני כל שינוי — מה זה שובר, אילו כפתורים רלוונטיים במצב החדש, מה חסר במסכים אחרים.
- **עיצוב בלבד:** שמור את כל שמות ה-attributes/signals/slots (כמו שנעשה ב-v3.01/v3.03). לוגיקה נשארת במקומה;
  אם חייבים להזיז — helper משותף, לא שכפול. השתמש בעזרי-UI הקיימים לפני שכותבים חדשים.
- מלכודות: בלי `QGraphicsDropShadowEffect` בכרטיסים, בלי Rubik, `clearContents()` לפני repopulate של קומבו-בטבלה,
  `setCurrentCell` ולא `selectRow`, גלילה אחת (`QScrollArea` יחיד) + סרגל תחתון מחוצה לה.
- כל טקסט חדש — עברית פשוטה, RTL.

## שלב 5 — אימות ושחרור (Definition of Done)
1. הרץ את הבדיקות הרלוונטיות למסך (`python test_X.py` עם Python 3.12) + `dev/stress_test.py` אם נגעת בטבלה.
2. **צילום אמיתי אחרי** — עדכן/צור `dev/_shot_<מסך>.py` עם assert-ים (ווידג'טים קיימים, גלויים, לא חורגים
   מרוחב החלון) ואמת את ה-PNG דרך Gemini (לא בצ'אט). השווה מול ההדמיה שאושרה — אם שונה מהותית, תקן.
3. בדוק גם ב-`ui_font_scale` גבוה (130%) שהפריסה לא נשברת.
4. עדכן `CLAUDE.md` (מקטע הלשונית — "עוצב מחדש vX.Y", שם סקריפט הצילום) ו-`NEXT_TASK.md`; אם למדת דפוס
   צילום/UI חדש — עדכן את הסקיל `visual-check`. מחק את `הדמיית_<מסך>.html` מהשורש או העבר ל-`dev/` (לא להשאיר
   קובצי תכנון בשורש).
5. שחרר לפי `manhal-haluka`: bump `version.py` → build → `Manhal-Haluka.exe` → commit/push → `gh release`.
   הודעת ה-commit בפורמט הערות-השחרור (כותרת עם `:` ואז פריטים בפסיקים), **בלי קרדיט Claude**.
6. סיים בהערת-שחרור קצרה ליהודה: מה השתנה במסך ומה זה נותן לו — בלי צעדים טכניים.
