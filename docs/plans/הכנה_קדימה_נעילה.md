## 0. תקציר והמלצה

**מה בונים:** כפתור "🔒 נעל רשימה" במסך החלוקה. רשימה שננעלה נשמרת כ"חלוקה מתוכננת" לרביעי מסוים. מי שבה:
1. **תפוס** — לא ייכנס לרשימה של שבוע אחר שנמצא בטווח התדירות שלו (חודשי: 3 שבועות לפני ואחרי; דו-שבועי: שבוע לפני ואחרי; שבועי: אף פעם לא נחסם).
2. **קפוא** — הרשימה לא משתנה מעצמה כשמשתנים נתונים (מישהו נוסף, הושהה, ועוד). התוכנה רק **מראה** מה השתנה, ורון מחליט.
3. **מסתיים לבד** — כשנרשמת חלוקה אמיתית באותו שבוע ("בוצעה"), או כשהשבוע עבר ולא נרשם כלום ("פגה"). בשני המקרים הנעילה מפסיקה לתפוס אנשים, כך שאף אחד לא נעלם לנצח.

**ההמלצה בשורה אחת:** לשמור כל רשימה נעולה כ**מפתח אחד בטבלת ההגדרות** (`planned_dist:<תאריך הרביעי>`, ערך JSON עם החברים) — בלי טבלה חדשה, בלי op סנכרון חדש ובלי שינוי ב-`sync.py`. הסיבה העיקרית: גרסה ישנה במחשב השני **מתעלמת בשקט** מכל op שהיא לא מכירה ו**לא חוזרת אליו אחרי העדכון**; הגדרה היא סוג רשומה שהיא כבר מכירה. פירוט והחלופות בסעיף 2.

**שני דברים שמורידים הכי הרבה סיכון:**
- **פריסה בשני שלבים.** קודם משחררים את מנגנון "תפוס" בלי שאפשר ליצור נעילה (אין שום שינוי התנהגות), מחכים ששני המחשבים מעודכנים (סעיף 5.6), ורק אחר כך משחררים את הכפתור.
- **נכשלים פתוח, לא סגור.** כל מצב לא ברור (נעילה שפגה, מקבל שנמחק, גרסה ישנה) = האנשים **כן** מופיעים ברשימה, עם הסבר. כפילות מבזבזת מוצר; מישהו שנעלם מהרשימה שבועות הוא נזק אמיתי.

### 2.2 מבנה הרשומה

- **מפתח:** `planned_dist:2026-10-28` (תמיד הרביעי; `weekday()==2` מאומת בשמירה).
- **זהות = התאריך.** לא guid: נעילה אחת לכל רביעי, ושני מחשבים שיוצרים נעילה לאותו רביעי מתכנסים לאותו מפתח (LWW), במקום שתי רשומות כפולות שצריך לאחד. זה סטייה מכלל "guid לכל שורה" ב-`db-migration`, והיא מכוונת: תאריך הוא מפתח יציב בין המחשבים (כמו מפתח הגדרה), בניגוד ל-id מקומי.

```json
{
  "v": 1,
  "week_wed": "2026-10-28",
  "dist_date": "2026-10-28",
  "name": "",
  "products": 60, "reserve": 8,
  "mode": "schedule",
  "note": "",
  "members": [
    {"g": "<guid מקבל>", "role": "main",    "kind": "reg", "note": "", "n": "<שם בזמן הנעילה>"},
    {"g": "<guid>",      "role": "reserve", "kind": "one", "note": "", "n": "..."}
  ],
  "removed": ["<guid>"],
  "created_at": "2026-10-18T20:00:00+00:00", "created_dev": "<device_id>",
  "updated_at": "2026-10-18T20:05:12+00:00", "updated_dev": "<device_id>",
  "deleted": 0
}
```

| שדה | משמעות / החלטה |
|---|---|
| `members[].g` | guid של המקבל. **לא `id` מקומי** (במחשב השני id מצביע על אדם אחר — `CLAUDE.md` סנכרון). |
| `role` | `main` = מקבל (תופס). `reserve` = המתנה (**לא** תופס, לא נרשם כברירת מחדל — כלל 3). |
| `kind` | `reg` קבוע שבתור · `one` חד-פעמי (הצעה אוטומטית או בחירה) · `man` הוספה ידנית. משמש לתצוגה ולהשוואה (סעיף 4.5), לא לחישוב. |
| `note` | ההערה לשורה (`_row_notes`, `group_update.py:1267`) — פר-שבוע, במקום הנוכחי שהוא זיכרון בלבד. |
| `n` | צילום שם — רק כדי להציג "נמחק: ‏…" כשהכרטיס כבר לא קיים. |
| `removed` | מי שהוסר ב-🗑 (`_removed_ids`, שורה 1272). בלעדיו, ההשוואה לנתונים החיים תציף את אותם אנשים כ"חסרים". |
| `mode` | מידע בלבד (איזה מצב בנה את הרשימה). הרשימה הנעולה מוצגת בלי קשר למצב שבקומבו. |
| `updated_at` | **"עכשיו" בזמן הכתיבה** (`database._utc_now`, `database.py:12`), לא תאריך עסקי. אותו ערך בדיוק משמש כאסימון לזיהוי התנגשות (5.3). |
| `deleted` | מחיקה רכה (ערך מינימלי, המפתח נשאר) — אין מחיקת הגדרות בסנכרון. |

**מה לא נשמר בכוונה** (מקור אמת יחיד, מלכודת "נגזרים לא נוסעים כערכים" ב-`db-migration`): תדירות, `last_distribution`/`next_distribution`, ניקוד, טלפון, שטח, נפשות. הכול נקרא חי מהכרטיס. תדירות שהשתנתה אחרי הנעילה משפיעה מיד על הטווח של "תפוס" — וזה נכון.

**נפח:** ~60 בייט לחבר. רשימה רגילה (~40–100 איש) = 3–7KB. רשימה גדולה כמו 25/8 (598) = ~36KB. כתיבה לסנכרון נשלחת כשורת יומן אחת לכל שמירה → עריכות מיידיות (4.3) מוסיפות עשרות KB ליום בשימוש כבד; הדחיסה ב-3MB מטפלת. ללא ניקוי אוטומטי בשלב ראשון (פריט S7 אופציונלי: נעילות ישנות מ-90 יום הופכות לטומבסטון קטן).

### 2.3 איך נעילה ממופה לרביעי

- המסך בונה רשימה לפי `selection.upcoming_wednesday(<התאריך שנבחר>)` (שלב 1, פרמטר `on_date`). זה גם המפתח: `week_wed = upcoming_wednesday(date_edit)`.
- **רישום** לעומת **הכנה** לא מתיישבים בחמישי–שבת: הכנה לתאריך חמישי 22/10 מציגה את רשימת 28/10; אבל רישום שתאריכו חמישי 22/10 שייך לשבוע של 21/10 (כלל 9). לכן נוסף `selection.round_wednesday(d)`:
  ראשון–רביעי → הרביעי שבו או אחריו · חמישי–שבת → הרביעי שלפניו. הוא **היחיד** שמשמש לזיהוי "בוצעה" (3.4) ולבדיקת התאריך ברישום (4.7).
- ⚠ **ממצא צדדי, לא קשור לנעילה:** `selection.cycle_wednesday` (שורה 98) מחזיר ליום ראשון את הרביעי **שלפניו** (אומת: ראשון 18/10 ← 14/10), בעוד כלל 9 ו-`next_due` (שורה 123–131) משייכים אותו לרביעי **שאחריו** (21/10). לכן `_one_time_turn` (שורה 155) נותן לחד-פעמי שקיבל ביום ראשון חזרה ב-11/11 במקום 18/11. סטייה של שבוע בהפסקת החד-פעמיים אחרי חלוקת ראשון–שלישי. לא לתקן כאן — לרשום ב-`NEXT_TASK.md`, ולהשתמש ב-`round_wednesday` בקוד החדש.

## 3. איך "תפוס בתכנון" נכנס לחישובים

### 3.1 הכלל המדויק (טהור, ב-`selection.py`)

```python
PLAN_GRACE_DAYS = 3        # עד שבת אחרי הרביעי עוד אפשר לרשום (כמו ROUND_WINDOW_DAYS)

def plan_interval_days(rec, cooldown_weeks) -> int:
    if is_regular(rec):                              # קבוע: לפי התדירות; תדירות ריקה (עדיפות 4) = שבועי
        return FREQUENCY_INTERVAL_DAYS.get((rec.get("frequency") or "").strip(), 7)
    return 7 * cooldown_weeks if cooldown_weeks > 0 else 7   # חד-פעמי: אותה הפסקה של כלל 7

def planned_elsewhere(rec, base_wed, plan_index, cooldown_weeks):
    """תאריך הרביעי של נעילה חיה שמחזיקה את האדם ושונה מ-base_wed וקרובה ממנו
    מ-interval ימים; אחרת None."""
    for p in plan_index.get(rec.get("guid"), ()):
        d = abs((p - base_wed).days)
        if 0 < d < plan_interval_days(rec, cooldown_weeks):
            return p
    return None
```

**למה `0 < d < interval` (ולא "קרוב אליו"):** זה אותו חשבון של `next_due`/`is_due` הקיימים, מצד אחר. אדם שקיבל ב-P חוזר בתור ב-`P + interval`. לכן שבוע Q חסום כש-`|Q−P| < interval`, ומותר כש-`≥ interval`.

| תדירות | חסום ב… | מותר מ… |
|---|---|---|
| שבועי / קבוע בלי תדירות | **אף שבוע** (7 לא קטן מ-7) | תמיד |
| דו-שבועי (14) | ±שבוע אחד | ±שבועיים |
| תלת-שבועי (21) | ±שבוע, ±שבועיים | ±3 שבועות |
| חודשי (28) | ±1, ±2, ±3 שבועות | ±4 שבועות |
| חד-פעמי (הפסקה 4 → 28) | ±1…±3 שבועות | ±4 שבועות. הפסקה 0 = כבוי: רק אותו שבוע |

**החלטות שנגזרות:**
- **רזרבה לא תופסת** (לא נרשמת, לכן לא "קיבלה"). אפשר להיות רזרבה בשתי נעילות.
- **סימטרי** (הוכרע — יהודה 18/10/2026, שאלה 1 בסעיף 10): נעילה של שבוע 4 חוסמת גם את שבוע 2. זה גם הכיוון שמונע כפילות כשמכינים שלא לפי הסדר.
- **שבוע של עצמה לא נחסם:** `0 < d`. שבוע שיש לו נעילה מוצג מהנעילה, לא מחושב.
- **רק נעילה חיה** (3.4). נעילה שבוצעה/פגה/נמחקה לא נכנסת ל-`live_plan_index`.

### 3.2 איך זה מתחבר בלי לכתוב `last`/`next` ובלי לשבור את `is_due`

מחקים את הדפוס של כלל 9 שכבר עובד: **`database.py` מתייג שורות, `selection.py` קורא את התג.**

1. `database.tag_planned(rows, base_wed)` (דומה ל-`tag_round_served`, `database.py:2478`): טוען פעם אחת `live_plan_index(today, exclude_wed=base_wed)`, ולכל שורה קובע `r["planned_elsewhere"] = <ISO של הנעילה | None>`. `exclude_wed` כדי שהרשימה החיה של שבוע (שמשמשת להשוואה בסעיף 4.5) לא תיחסם על ידי הנעילה של אותו שבוע עצמו.
2. `selection.is_due` (שורה 188): **בשורה הראשונה** — `if rec.get("planned_elsewhere"): return False`. לפני `last is None`, כדי שגם קבוע חודשי שמעולם לא קיבל ונעול בשבוע אחר ייחסם.
3. `selection.not_due_reason` (שורה 226): ענף חדש — `"נעול ברשימה של DD/MM"`, כך שהחלון "מקבל שלא בתור השבוע" (`group_update.py:3389`) מסביר את הסיבה.
4. **בלי תג — בלי חסימה** (ברירת מחדל פתוחה, כמו `round_served`). בדיקות והקוראים הישנים לא מושפעים.

**נקודות החיבור ב-`database.py`** (שלב 1 כבר מעביר להן `on_date`):

### 3.4 מצב נעילה (נגזר, לא נשמר)

```python
def plan_state(week_wed, today, executed: bool) -> str:
    if executed:                                  return "executed"
    if today > week_wed + timedelta(days=PLAN_GRACE_DAYS): return "stale"
    return "current" if week_wed == upcoming_wednesday(today) else "future"
```
- `executed` = קיימת אצווה **רגילה** (`COALESCE(holiday,'')=''`, בלי חג/בונוס) ש-`round_wednesday(dist_date) == week_wed`. מחושב בשאילתה אחת על `dist_batches` בטווח כל הנעילות, בעזרת `_regular_rounds_sql()` (`database.py:2452`, עובד גם על `dist_batches` כי יש שם עמודות `holiday` ו-`dist_date`).
- **למה נגזר ולא נשמר:** (א) אפס סנכרון נוסף; (ב) מחיקת האצווה (`delete_batch`, 2557) מחזירה את הנעילה לחיים אוטומטית; (ג) המחשב השני שרשם — מתעדכן בלי op.
- חיה (תופסת) = `current` או `future` בלבד.
- **אחרי `executed` ההיסטוריה היא האמת** — מי שנרשם קיבל ו-`next_due` מזיז אותו; מי שלא נרשם "לא הגיע" וחוזר לתור.

### 4.1 טבלת מצבים

### 4.2 יצירה — כפתור "🔒 נעל רשימה"

- **מתי גלוי:** שלב הכנה בלבד (`_stage == "prep"`, ליד הדפסה/PDF, `group_update.py:2017`), חלוקה **רגילה** (לא מצב חג, `chk_bonus` לא מסומן), מוצרים > 0 ורשימה לא ריקה (כלל 6/7.10: בלי מוצרים אין רשימה בכלל), ו-`upcoming_wednesday(date_edit) >= upcoming_wednesday(היום)` (לא נועלים תאריך עבר/רישום רטרואקטיבי). אחרת מוסתר/נעול עם הסבר ב-tooltip.
- **מה נשמר** — מה שעל המסך ברגע הלחיצה: חברי main/reserve לפי `_rows_data` (כולל הוספות ידניות), `_removed_ids`→`removed`, `_row_notes`→`note`, מוצרים/רזרבה, שם, הערה כללית, מצב.
- **חד-פעמיים בשבוע עתידי (הכרעה 3):** בלחיצה על "נעל" בתחזית, המנות הפנויות לחד-פעמיים (`compute_suggested_n(..., on_date)`) מתמלאות **אוטומטית** בהצעה לפי התור הקבוע (`selection.plan_one_time` עם `scoring.ONE_TIME_QUEUE_WEIGHTS`, רק מי שמקבל `ROLE_MAIN`) ונשמרות כ-`kind="one"`. מציגים את ההצעה בחלון אישור קצר לפני הנעילה (שמות + "שנה"). בשבוע האמיתי נשארת הבחירה הידנית הקיימת — מה שנבחר שם הוא מה שננעל.
- **אם כבר קיימת נעילה לאותו רביעי** — הכפתור הופך ל"🔓 בטל נעילה" (לא יוצרים כפילות; המפתח ייחודי).
- **הגלובליים לא נוגעים:** נעילה של השבוע האמיתי **לא מאפסת** את `weekly_extra_ids`/`available_products`. בזמן נעילה המסך מציג את הנעילה ולא קורא/כותב אותם; ביטול נעילה מחזיר אותם כפי שהיו (עריכות שנעשו בזמן הנעילה לא חוזרות — האישור אומר זאת). כך גם גרסה ישנה במחשב השני רואה בדיוק את מה שראתה.

### 4.3 עריכה (כשנעולה)

כל פעולה נכתבת **מיד** (כמו `_persist_extras` היום, `group_update.py:1367`) כ-`save_plan` עם אסימון `expected_updated_at`. פעולה = לחיצה מכוונת, לכן אין צורך ב"שמור" נפרד. פעולות:
- 🗑 הסרה ← מועבר מ-`members` ל-`removed`. המוצר שהתפנה **לא** מוקצה אוטומטית להבא בתור (הרשימה קפואה); מציגים "נשארו X מוצרים לא מוקצים" ורון מוסיף ידנית או לוחץ "עדכן מהנתונים".
- "＋ הוסף מקבל" ← `kind="man"`, `role="main"`.
- הערה בשורה ← `note`.
- שינוי מוצרים/רזרבה ← מעדכן את השדות **בלי** לשנות חברים (הרשימה קפואה). מוצג "מספר החברים שונה ממספר המוצרים — לחץ 'עדכן מהנתונים' אם רוצים לבנות מחדש".
- מצב הקומבו ושאר המצבים המתקדמים: **מושבתים** כשנעולה ("נעולה — נבנתה במצב X").

### 4.4 תצוגה — איך נטענת נעילה למסך

`refresh()` (`group_update.py:2327`) מקבל ענף בראש: אם יש נעילה **חיה** לרביעי של התאריך שנבחר —
`self._rows_data = db.plan_rows(plan)` ומדלגים על כל לוגיקת המצב/החיתוך/`_extra_ids`/`_removed_ids`. `plan_rows`:
- טוען כרטיס לפי guid. **נמחק** ← מדולג (ומוצג בבאנר "N חברים נמחקו"). **מושהה** (`status != 'פעיל'`) ← לא נכלל ב-`week_rows()` ובפלטים; מוצג באפור בעורך עם "הושהה — לא ייכלל". חריג: `kind="man"` שנוסף במכוון נשאר עם תג `_inactive` כמו היום (`_extra_recipients`, שורה 2025–2054).
- מתייג `_reserve` ל-`role="reserve"`, `_extra` ל-`kind in (one, man)`, ומחשב `days_since`/`need_score` **לתצוגה בלבד** (כדי שלחיצה על שורה תסביר ניקוד).
- מחזיר באותו סדר שנשמר (סדר הנעילה, בלי מיון מחדש).

### 4.5 קפואה, אבל לא עיוורת — באנר השוואה

כשהנעילה פתוחה (ובמצב `schedule` בלבד, ראה 10 "לא ידוע"), בונים ברקע את הרשימה החיה לאותו שבוע עם `exclude_wed=week_wed` ומשווים (רק קבועים):
- **חדשים בתור שאינם בנעילה** (ולא ב-`removed`) — למשל מקבל שנוסף אחרי הנעילה. הסכנה האמיתית: קבוע חדש "חייב מיד" ולא ייכנס. מוצג באדום.
- **בנעילה אבל כבר לא בתור** — הושהה, נמחק, תדירות שונתה, קיבל במקום אחר.
- כפתור אחד "עדכן את הרשימה הנעולה": חלון עם שתי רשימות שמות (יתווספו / יוסרו), `kind="man"` תמיד נשאר, ורק אחרי אישור כותב.
- לעולם לא מתעדכן מעצמו.

### 4.6 ביטול נעילה ומחיקה

"🔓 בטל נעילה" = `delete_plan` (מחיקה רכה). אישור קצר ("מי שבה יחזור להיות זמין לשבועות אחרים"). **לא** נוגע בהיסטוריה/בכרטיסים. "חלוקה חדשה" (`_reset_for_new`, שורה 3409) מאפסת את **הגלובליים (טיוטת השבוע הנוכחי) בלבד**; כשהמסך על שבוע נעול היא שואלת "הרשימה נעולה — לבטל גם את הנעילה?" ברירת מחדל "לא" (ואז לא נוגעת בנעילה).

### 4.7 כשנרשמת חלוקה אמיתית

`_save` (`group_update.py:2815`) לא משתנה בהיגיון: הרשימה שבמסך (= חברי הנעילה) היא `_rows_data`, הסימונים נרשמים כרגיל דרך `bulk_add_distributions` (2158). **שום קריאה לנעילה** — "בוצעה" נגזרת. שני שינויים קטנים:
1. **בדיקת תאריך** לפני רישום: `round_wednesday(date_edit) != week_wed של המסך` ← אישור ("התאריך שנבחר שייך לשבוע החלוקה של DD/MM ולא של DD/MM. להמשיך?"). חמישי–שבת הם המקרה הנפוץ.
2. אחרי `_after_round_recorded` (2920) — הנעילה "בוצעה" וכבר לא נראית כנעולה. המסך נשאר בתאריך (לא קופץ).

**חסימת רישום לשבוע עתידי — כבר בשלב 1** (0.1): נעילה של שבוע עתידי נשארת בלי אפשרות רישום עד שהוא הופך לשבוע הנוכחי. (הרקע: `_recompute_recipient_dates` מתעלם בשקט מתאריך אחרי הרביעי הקרוב, `database.py:2537`, ולכן רישום עתידי היה נכתב להיסטוריה בלי להזיז תור.)

### 4.9 מה פר-שבוע ומה גלובלי (שאלת `weekly_extra_ids` וחבריה)

היום: `weekly_extra_ids`/`weekly_reserve_ids` (`group_update.py:1364–1380`), `available_products`, `reserve_count` (שורות 2099/2106) — **הגדרה אחת מסונכרנת** לשבוע האחד שעובדים עליו. `_removed_ids` ו-`_row_notes` — זיכרון בלבד.

**כלל חדש — שלוש קטגוריות, ואף אחת לא כותבת לגלובליים משבוע שאינו האמיתי:**

| שבוע | איפה יושבים בחירות/הסרות/הערות/מוצרים/רזרבה |
|---|---|
| **נעול** | **בתוך הנעילה** (`members`, `removed`, `note`, `products`, `reserve`). המסך לא קורא ולא כותב את הגלובליים |
| **השבוע האמיתי בלי נעילה** | בדיוק כמו היום (הגדרות גלובליות מסונכרנות). תאימות לאחור מלאה, גם עם גרסה ישנה במחשב השני |
| **תחזית עתידית בלי נעילה** | **לקריאה בלבד** (שלב 1). עריכות — 🗑 / ＋ הוסף / "בחר חד-פעמיים" / הערות — **מושבתות** עם tooltip "נעל את הרשימה כדי לערוך". "מוצרים זמינים" ו"רזרבה" נשמרים **בזיכרון בלבד** פר-שבוע (`self._forecast_counts[week_wed]`) ולא כותבים `available_products`/`reserve_count` |

- **למה השבתה ולא "טיוטה בזיכרון" מלאה:** מונע דליפה לשבוע האמיתי (0.1 סעיף 3) בלי מנגנון חדש; הנעילה היא כבר הדרך לשמור. עלות: לחיצה אחת נוספת לפני עריכה.
- **מעבר תאריך** שבוע א׳ ← שבוע ב׳: מציגים את הנעילה/התחזית של ב׳; הערכים בזיכרון של א׳ נשמרים ב-`_forecast_counts` ולא מדלפים. ערך ברירת מחדל למוצרים בתחזית חדשה: הערך של השבוע האמיתי, כהצעה גלויה (שאלה 3 בסעיף 10).
- **חד-פעמיים בתחזית:** מוצעים אוטומטית **בשעת הנעילה** (4.2) לפי `scoring.ONE_TIME_QUEUE_WEIGHTS` (50/25/25). הם הופכים ל-`kind="one"` ובכך **תופסים** הפסקה של 4 שבועות — וזה מה שגורם לרוטציה נכונה בין השבועות (תחזית של שבוע 3 כבר לא תציע את אותם חד-פעמיים). אם שלב 1 יציג הצעה גם בתחזית הלא-נעולה — מצוין, אבל לא נדרש כאן.

## 5. סנכרון

### 5.1 מה נוסע ואיך (חלופה ג׳)

- נוסע ב-op **`setting`** הקיים: `database.set_setting` → `_sync_log("setting", {key, value})` (`database.py:795`) → `log_change` (`sync.py:477`) → `_apply_setting` (`sync.py:1158`). **אין שינוי ב-`sync.py`** — לא ב-`_APPLIERS`, לא ב-`_snapshot_body`, לא ב-`_TOMBSTONE_OPS`.
- המפתח `planned_dist:*` לא מתחיל בתחילית מוחרגת (`sync_`, `export_dir_`) ולא ב-`EXCLUDED_SETTINGS` ← מסונכרן. (נבדק: אין היום מפתח שמתחיל ב-`plan`.)
- **LWW:** `_apply_setting` דוחה רשומה אם `rec.ts <= known[key]` (`sync.py:1163`). `rec.ts` = `_utc_now()` ברגע ה-`log_change`, כלומר **"עכשיו" בכתיבה — לא תאריך הרביעי** (הלקח של v2.97 ב-`db-migration`). נעילה לרביעי עוד חודש נכתבת עכשיו, ולכן עריכה מאוחרת יותר בכל מחשב תנצח. בדיקה ייעודית (S2).
- **הצטרפות מחשב ודחיסה:** `snapshot` ו-`compact_journal` שולחים את כל ההגדרות עם חותם אמיתי (`sync.py:608–615`), לכן נעילות נוסעות בלי קוד.
- **רענון אחרי סנכרון:** `refresh()` כבר קורא `_load_extras` ומציין "בחירה שנעשתה במחשב השני מגיעה דרך רענון הסנכרון" (`group_update.py:2327–2330`). נעילה שהגיעה תוצג באותו מסלול. לוודא בבדיקה (U10).

### 5.2 שני מחשבים עורכים אותה נעילה

- **מקרה רגיל (ברשת, מקוון):** רון עורך, הכתיבה נשלחת ב-10–20 שנ'. מחשב שני שפתח את אותה נעילה לפני העדכון ושומר אחרי — **אסימון `expected_updated_at`** (דפוס `save_card_edit`, `tabs/recipients.py`): אם הערך השמור שונה ממה שנטען ← `PlanConflict` ← "הרשימה הנעולה שונתה במחשב אחר. לטעון מחדש (העריכה שלך תאבד) / לדרוס?" ברירת מחדל "לטעון".
- **מקרה מנותק (שני המחשבים עורכים אופליין):** LWW לפי **רשימה שלמה** — הכותב המאוחר מנצח, העריכות של האחר נעלמות. מקובל (עורך אחד בפועל); מקטינים נזק בכך שהעורך מציג "נערכה לאחרונה ע״י <שם מחשב> ב-HH:MM" (`updated_dev` + `sync.device_name()`), כך שדריסה נראית.
- **שני מחשבים יוצרים נעילה לאותו רביעי** ← אותו מפתח ← נשארת אחת (LWW). אין כפילות לאחד.
- **מחיקה מול עריכה** ← LWW על המפתח (`deleted:1` הוא עוד כתיבה).

### 5.3 תאימות לגרסה ישנה במחשב השני

מה שקורה לגרסה ישנה (ללא שינוי בקוד שלה):
- מקבלת `setting` עם מפתח לא מוכר ← `INSERT OR REPLACE` לטבלת ההגדרות. **בלי קריסה, בלי איבוד נתונים.** אף מסך לא עובר על כל המפתחות (נבדק: כל קריאות `FROM settings` ממוקדות — `main.py:1166,1209`, `database.py:1805`, סנכרון).
- **לא מכבדת נעילות** — הרשימות שלה לא מכירות "תפוס". היא עלולה להכניס אדם נעול. זה חלון הסיכון היחיד.
- **אחרי שתתעדכן** — הנעילות כבר בטבלה שלה ופועלות מיד. אין "שליחה חוזרת", כי לא הייתה הודעה שנפלה.
- לעומת זאת בחלופה ב׳/א׳ (op חדש): `pull_changes` מדלג ומקדם `seq` ו-offset (`sync.py:1311–1313`); המחשב המעודכן לא ישלים את מה שפספס בלי מנגנון (נספח א׳).

### 5.4 איך סוגרים את חלון הסיכון — פריסה בשני שלבים

1. **גרסה X (מנגנון בלבד):** `selection`/`database` עם `tag_planned`/`live_plan_index`/`round_wednesday` — אבל **אין כפתור נעילה**, ולכן אי אפשר ליצור נעילה. אפס שינוי התנהגות. מתעדכנים שני המחשבים.
2. **גרסה X+1 (כפתור):** מציגים "🔒 נעל" רק אם:
   - אין סנכרון, או
   - כל המחשבים האחרים מדווחים גרסה ≥ X (קוראים `app_version_<device>` — הערכים `"גרסה|שם"` — אותו מקור של `_check_peer_updates`, `main.py:1200–1228`).
   אחרת הכפתור נעול עם "המחשב השני עדיין בגרסה ישנה — הוא לא יכבד נעילות. עדכן אותו קודם".
- **המחשבים מנותקים כרגע (6/10/2026) ויהודה לא רוצה לחבר.** בלי סנכרון פעיל לשום מחשב אחר — הכפתור זמין. כשיתחברו, נעילות שנוצרו מקומית יגיעו ב-`enable_sync(seed=True)` (כל ההגדרות נשלחות). **את כל זה אי אפשר לאמת בשטח** — רק ב-`test_sync.py` עם שני מחשבים מדומים (סעיף 7).

### 5.5 מה לא משתנה בסנכרון

`bulk_add_distributions` ו-`batch_add` (שורות 2158/2250) — ללא שינוי. "בוצעה" נגזרת משם אצל כל מחשב לבד. `rec_merge` ו-`rec_delete` — ללא שינוי.

### 6.2 צינתוקים ומיילים — הסיכון הכי חשוב בפלטים
